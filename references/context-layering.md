# Context Layering

Agents load knowledge in layers. Base agent definitions are global. Project-specific knowledge is added via context files in `.work/context/`.

## Layer Order (bottom to top)

```
4. .work/context/<agent>.md      ← Agent-specific project knowledge (highest priority)
3. .work/context/<department>.md ← Department-wide project knowledge
2. .work/context/project.md     ← Shared project knowledge (all agents)
1. ~/.claude/agents/do-<agent>.md ← Base agent definition (global)
```

Each layer is optional. Agents use whatever layers exist.

## Context Directory Structure

```
.work/context/
├── project.md          # ALL agents read this
├── engineering.md      # Engineering agents read this
├── business.md         # Business agents read this
├── people.md           # HR, legal agents read this
├── product.md          # Product, design agents read this
├── coder.md            # Only do-coder reads this
├── security.md         # Only do-security reads this
├── marketer.md         # Only do-marketer reads this
└── ...                 # Any agent can have a specific override
```

## Department Mapping

| Department File | Agents That Read It |
| --------------- | ------------------- |
| `engineering.md` | coder, security, reliability, qa, devops |
| `business.md` | strategist, marketer, sales, finance, ops |
| `people.md` | hr, legal |
| `product.md` | product, designer |

Cross-cutting agents (researcher, reviewer, writer) read `project.md` only, plus their own agent-specific file if it exists.

## What Goes in Each Layer

### project.md (everyone reads)
- Project name and description
- Tech stack summary
- Repository structure overview
- Key conventions (naming, file organization, etc.)
- External services and integrations
- Team size and structure
- Deployment targets

### Department files (department reads)
- Department-specific conventions
- Tools and frameworks in use
- Known issues and gotchas
- Existing patterns to follow
- Things to avoid

### Agent-specific files (one agent reads)
- Deep domain knowledge for this project
- Specific libraries and their configurations
- Known vulnerabilities or technical debt
- Custom checklists beyond the base agent's defaults
- Historical decisions and their rationale

## How Agents Load Context

When an agent is dispatched, the orchestrator instructs it to read context files in order:

```
1. Read .work/context/project.md (if exists)
2. Read .work/context/<department>.md (if exists)
3. Read .work/context/<agent-name>.md (if exists)
4. These override/extend the base agent's knowledge
```

The agent's base definition (global) provides the role, principles, and checklist.
The context files provide project-specific knowledge that customizes behavior.

## Generation

Context files are generated by:
- `/do:discover` - scans an existing codebase and generates context files
- `/do:setup` - interactive setup for new/greenfield projects
- Manual editing - you can always edit context files directly

Context files can be regenerated anytime. They are not append-only.
